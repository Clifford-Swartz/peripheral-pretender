# CCL (Configurable Custom Logic, IP U2225) on the PIC32CM MC00: research notes

Gathered 2026-10-20 to plan a QEMU model of the CCL and a silicon check on the bare EV15N46A. No
hardware was touched. Sources, most authoritative first:

1. **PIC32CM MC00 Family Data Sheet DS60001638E** (the PDF from microchip.com, read with
   pdftotext; its cover reads "5-Volt Motor Control MCU"): chapter 35 "Configurable Custom Logic
   (CCL)", pp. 709-726. Below, "§35.x" means this document. Also §1 Table 1-1 (configuration
   summary), §4.4 (48-pin pinout and multiplexing), §27.6 and 27.7 (PORT), Table 28-x (EVSYS
   generators and users), §33.6.2.6.1 (TC waveform output), §34 (TCC) and §38.7 (AC).
2. **Errata DS80000905G** (newer than F): it lists **no CCL errata**. The one relevant item is
   §1.4.1, which says not to use the AC INTREF; use the DAC as the AC's internal reference.
3. DFP PIC32CM-MC_DFP 1.4.67: `PIC32CM1216MC00048.atdf` (module CCL U2225 1.0.1, lines 130-172
   and 1486-1566) and `include/component/ccl.h`.
4. `devices/pic32cm1216mc00048.json` (instance, signals, GCLK, events). For the same IP on the
   other two targets: `devices/pic32cm5164jh01100.json` and `devices/atsame51j20a.json`.
5. Two other data sheets, read only for the per-device differences in §2: **DS60001632H**
   (PIC32CM JH00/JH01, CCL chapter 37) and **DS60001507N** (SAM D5x/E5x, CCL chapter 41).
6. Harmony CSP `peripheral/ccl_u2225` (`config/ccl.py`, `templates/plib_ccl.c.ftl`, master branch).
7. PIC32CM MC00 Curiosity Pro user guide DS70005440A, which is the source for the board wiring in
   §5.1. It came back through the Microchip docs MCP.

Search warning (as in `ac-u2245.md`): the docs MCP returns the SAM D21 data sheet for the title
"Low-Power, 32-bit Cortex-M0+ MCU with Advanced Analog and PWM". The SAM D21 has no CCL at all.
The MC00 data sheet's onlinedocs GUID is 0D44A543-8D6E-4F72-814C-6F4857061C73, and its search
title is "5-Volt Motor Control MCU". The index holds only the text parts of §35. The input
selection (§35.6.2.4) and sequential logic (§35.6.2.7) sections come back as images, so these
notes use the PDF. onlinedocs pages also fail in a headless browser.

Side finding (not CCL): `hw/timer/mchp_tcc.c` cites "DS60001638E chapter 31", but the TCC is
chapter **34** in DS60001638E. In the SAM D21 data sheet the TCC is chapter 31. Likewise,
`mchp_evsys.c` cites chapter 27, but the EVSYS is chapter **28** (the PORT is 27). Re-check
anything that was taken from those citations.

**Twin today:** there is no CCL model. `pic32cm_models[]` in `hw/arm/pic32cm_soc.c` has no CCL
entry, so the CCL is a plain `mchp-regblock` that stores its registers and does nothing else.
There is no `overlays/ccl_u2225.yaml` either, so the generated table has `enprot` = 0 everywhere
and the twin accepts writes that silicon would ignore while the CCL is enabled.

Marks used: **[guess]** is inference, not documented. **[silicon?]** is a question for the test
plan.

## 2. Register map (§35.7, ATDF, ccl.h)

Five 8- or 32-bit registers, 0x18 bytes in all. None of them is synchronized: there is no
SYNCBUSY register, and Harmony writes SWRST and then the configuration with no wait.

| Off | Register | Reset | Fields (bit) | Protection |
|---|---|---|---|---|
| 0x00 | CTRL (8) | 0x00 | SWRST (0, W), ENABLE (1), RUNSTDBY (6). Mask 0x43 | PAC. **RUNSTDBY is enable-protected** when CTRL.ENABLE = 1 (§35.7.1 note: "CTRL register (except the bits ENABLE & SWRST) is Enable Protected") |
| 0x04 | SEQCTRL0 (8) | 0x00 | SEQSEL[3:0]: 0 DISABLE, 1 DFF, 2 JK, 3 LATCH (gated D), 4 RS; 5-15 reserved. Pair LUT0/LUT1 | PAC, enable-protected (by CTRL.ENABLE) |
| 0x05 | SEQCTRL1 (8) | 0x00 | same, pair LUT2/LUT3 | PAC, enable-protected |
| 0x08 + 4n | LUTCTRLn (32), n = 0..3 | 0x00000000 | ENABLE (1), FILTSEL[1:0] (5:4: 0 DISABLE, 1 SYNCH, 2 FILTER, 3 reserved), EDGESEL (7), INSEL0 (11:8), INSEL1 (15:12), INSEL2 (19:16), INVEI (20), LUTEI (21), LUTEO (22), TRUTH[7:0] (31:24). Reserved bits 0, 2, 3, 6, 23 | PAC. Enable-protected **except ENABLE** (§35.6.2.1) |

Enable protection. The rules come from §35.6.2.1 and the register notes:
- "The following bits are enable-protected, meaning that they can only be written when the CCL
  module is disabled (CTRL.ENABLE = 0): SEQCTRLx.SEQSEL, and LUTCTRLn except the ENABLE bit."
- "Enable-protected bits in the LUTCTRLn registers can be written at the same time as
  LUTCTRLn.ENABLE is written to '1', but not at the same time as LUTCTRLn.ENABLE is written to '0'."
  This sentence reads as if the protection were keyed to each LUT's own ENABLE, which contradicts
  the first rule and the register note ("LUTCTRLn register is Enable Protected when
  CCL.CTRL.ENABLE = 1"). Harmony avoids the question: it writes SWRST, then SEQCTRL, then each
  LUTCTRL **with ENABLE set**, and only then CTRL. **[silicon?]** (E0).
- Can LUTCTRLn.ENABLE be toggled while CTRL.ENABLE = 1? The text says ENABLE is excluded from the
  protection, so yes **[silicon?]**.
- Sequential logic: "While configuring the sequential logic, the even LUT must be disabled. When
  configured the even LUT must be enabled" (§35.6.2.7 note).
- "When using sequential logic the control register enable must be written twice when enabling
  (CTRL.ENABLE = 1)" (§35.6.2.2). This sentence appears **only in the MC00 data sheet**; it is not
  in DS60001632H or DS60001507N. Harmony writes CTRL once. **[silicon?]** (E12).
- The generic `mchp-regblock` enable check (CTRL at offset 0, ENABLE = bit 1) matches CTRL here.
  An overlay could therefore use `enable_protected: all` for SEQCTRL, `{all_except: [ENABLE]}`
  for LUTCTRL and `{all_except: [SWRST, ENABLE]}` for CTRL, with `self_clearing: [SWRST]`.

SWRST: "resets all registers in the CCL to their initial state, and the CCL will be disabled"
(§35.6.2.2). The bit is documented as W, but its value table says "1 = the reset operation is
ongoing". Whether it reads back 1 for a while is **[silicon?]**. SWRST under PAC write protection
raises a PAC error (§35.6.2.2).

INSEL values (ATDF value group CCL_LUTCTRL__INSEL; DS §35.7.3):

| Value | MC00 1.0.1 and E51 1.1.0 | JH01 2.0.0 |
|---|---|---|
| 0x0-0x9 | MASK, FEEDBACK, LINK, EVENT, IO, AC, TC, ALTTC, TCC, SERCOM | same |
| 0xA | reserved | ALT2TC (TC n+4) |
| 0xB | reserved | ASYNCEVENT (event input without the edge detector) |
| 0xC-0xF | reserved | reserved |

The MC00 §35.6.2.4 text still mentions ASYNCEVENT and a "second alternative TC(n+4)"; this was
copied from the JH01 text, and the MC00 register table marks 0xA-0xF reserved. The E5x data sheet
revision history says both "were removed". The 4-bit field stores 0xA-0xF (the write mask covers
all 4 bits) **[guess]**. What the hardware does with them on MC00 is **[silicon?]** (E6).

## 4. LUT and output behaviour

### 4.1 Truth table (§35.6.2.3, Table 35-1, Fig. 35-2)

`OUT = TRUTH[(IN2 << 2) | (IN1 << 1) | IN0]`: **IN0 is bit 0 of the index**. For example,
TRUTH 0x80 = AND3, 0xFE = OR3, 0x96 = XOR3 (odd parity), 0xE8 = majority, 0xAA = buffer of IN0,
0x55 = NOT IN0, 0xCC = buffer of IN1, 0xF0 = buffer of IN2. A masked input is 0, so with
everything masked OUT = TRUTH[0]. The output is combinational from the inputs and may glitch
(§35.6.2.5).

### 4.2 Per-LUT output pipeline (Fig. 35-1, §35.6.2.5-35.6.2.6)

`inputs → truth table → [filter or synchronizer] → [edge detector] → (even LUT: sequencer) → OUT`

- **FILTSEL** (§35.6.2.5): 1 SYNCH, 2 FILTER. "When a filter is enabled, the OUT output will be
  delayed by two to five GCLK cycles." Event inputs are filtered too. Fig. 35-12 shows four
  flip-flops on GCLK_CCL with a common clear, a gate and the FILTSEL mux. Reading of the figure
  **[guess]**: SYNCH is two flip-flops (2 cycles, plus up to 1 cycle of phase), and FILTER
  passes a change only when the last 3-4 samples agree, rejecting shorter pulses (about 4-5
  cycles). The exact latency and the shortest pulse that passes are **[silicon?]** (E13). "One
  APB clock after the corresponding LUT is disabled, all internal filter logic is cleared."
- **EDGESEL** (§35.6.2.6): "generate a pulse when detecting a rising edge on its input. To
  detect a falling edge, the TRUTH table should be inverted." The data sheet gives no pulse
  width; one GCLK_CCL cycle **[guess]** (E14). The filter or synchronizer "must be enabled" to
  avoid "unpredictable behavior". The edge detector logic is cleared one APB clock after the LUT
  is disabled.
- GCLK_CCL is needed for EVENT inputs, the filter, the edge detector and the sequencer
  (§35.6.2.1). The pure combinational path works without it. What a filtered LUT outputs with
  GCLK_CCL stopped is **[silicon?]**.

### 4.3 Sequential logic (§35.6.2.7, Tables 35-2 to 35-5, Figs. 35-14 to 35-17)

Pair N = (LUT 2N, LUT 2N+1). The even LUT drives D/J/S, the odd LUT drives G/K/R.

| SEQSEL | Behaviour | Clocking | Clear |
|---|---|---|---|
| 1 DFF (gated D flip-flop) | R = 1: clear. G = 1: OUT ← D. G = 0: hold | "refreshed on rising edge of the GCLK_CCL" | The even LUT disabled clears it asynchronously; R is held for one APB cycle |
| 2 JK | 00 hold, 01 clear, 10 set, 11 **toggle** | GCLK_CCL rising edge, so J = K = 1 toggles every GCLK_CCL cycle (a GCLK/2 square wave) **[guess from the table + clocking]** | as DFF |
| 3 LATCH (gated D latch) | G = 0 hold, G = 1 transparent (OUT = D) | Not stated; a latch is level-sensitive **[guess: asynchronous]** | The even LUT disabled clears it: "G forced enabled for one more APB clock cycle, and D to zero" |
| 4 RS latch | S R: 00 hold, 01 clear, 10 set, **11 forbidden** | Not stated **[guess: asynchronous]** | The even LUT disabled: "R forced enabled one more APB cycle, S to zero" |

Fig. 35-1 shows the sequencer between LUT0 and the "OUT0 / Event System / I/O" box, and LUT1
going straight to OUT1. So with SEQSEL ≠ 0, **OUT[2N] (pad and LUTOUT event) carries the
sequencer output, and OUT[2N+1] still carries the odd LUT's own output** (reading of the figure,
E12). FEEDBACK (§3) returns SEQ[N] to both LUTs of the pair.

### 4.4 Where the output goes

- **Pad**: CCL OUT[n] on PMUX function I (OUT3 also J), see §5.1. The PORT gives up direction and
  drive to the peripheral (§27.6.1). With PINCFG.INEN = 1 the "physical pin state may still be
  read from IN" (§27.7.14, PMUXEN). What the pad does while the LUT or the CCL is disabled
  (driven 0, or released like a disabled TCC, which on silicon leaves the pad floating with the
  pull off) is **[silicon?]** (E1).
- **Event**: generator CCL_LUTOUT_n (77+n) when LUTEO = 1: "OUTn: Lookup Table Output Value"
  (§35.6.3). This is the output **level**. EVSYS edge detection (EDGSEL) turns it into events on a
  sync/resync channel, and an async channel passes the level. LUTEO = 0 gives no event (level
  held at 0 **[guess]**).
- **Other LUTs**: LINK (to LUT n-1) and FEEDBACK (the sequencer, to both LUTs of the pair).
- **Other peripherals**: **only through EVSYS**. There is no direct CCL → TC/TCC path on this
  device (§35.6.3 lists only the event outputs). The useful users of LUTOUT are TC0-4 EVU (any
  path), TCC0-2 EV0/EV1/MCx (asynchronous only), PORT EV0-3 (asynchronous only), ADC/SDADC/DAC
  start, AC start, DMAC channels, PDEC, MTB, and another LUT's LUTIN.
- **No interrupt.**

### 4.5 Disabled and standby (§35.6.2.2, §35.6.4)

- A disabled LUT or a disabled CCL outputs 0 **[guess]**. The truth path runs without a clock.
- Standby with RUNSTDBY = 0: GCLK_CCL stops. "If the Filter, Edge Detector or Sequential logic are
  enabled, the LUT output will be forced to zero in STANDBY mode. In all other cases, the TRUTH
  table decoder will continue operation." With RUNSTDBY = 1, GCLK_CCL keeps running in standby.

## 5. Fitting it into pp-qemu (suggestions, not facts)

How the existing models connect (read 2026-10-20):
- **Outputs to pads**: `pic32cm_connect_pads()` turns each signal GROUP[n] that has a PMUX
  function into the model's GPIO out `"pad-<group>"[n]`, wired to PORT `"pmux-in"[pin*16+f]`, and
  an optional GPIO in `"pad-<group>-active"[n]` driven by PORT `"pmux-active"`. A signal on
  several pads fans out through a split-irq. For the CCL that means `"pad-out"[4]` (levels 0/1;
  `MCHP_PORT_PAD_HIZ` (-2) if E1 shows a released pad) and `"pad-out-active"[4]`.
- **Inputs from pads: missing.** The PORT exports pad levels to a peripheral function only for
  function A (EIC, `"func-a"`). The CCL IN[0..11] pads (I/J) need a general path, for example a
  PORT GPIO out `"func-in"[pin*16+f]` (the pad level while pin `pin` is muxed to function `f`,
  else 0) that the SoC wires from the signal table's input groups. Two pads can carry the same
  IN[x] (IN0 on PA04/PA16/PB22). If both are muxed, OR them as `pic32cm_connect_eic()` does, or
  take the first **[silicon?]** (E4). SERCOM RX, TC capture, PDEC and GCLK_IO inputs would reuse
  the same path. The PORT model already keeps the pull resistor on input-function pads (EIC,
  silicon), which matters for E2.
- **Events**: `pic32cm_connect_events()` derives GPIO names from the event table, giving GPIO out
  `"lutout-event"[4]` (the level, not pulses) and GPIO in `"lutin-event-in"[4]`. The CCL user is
  always ready (no `"lutin-event-busy"`) **[guess]**. Async channels hand the user the generator
  level, sync/resync channels a pulse per edge (`mchp_evsys.c`). The CCL must then apply its
  own rising/INVEI edge detector clocked by GCLK_CCL.
- **TCC WO**: `mchp-tcc` exports `"pad-wo"[8]`, but each line can connect to only one sink (the
  PORT, directly or through a split). The SoC must always split TCCn WO[0..2] so the CCL gets a
  copy. The TCC also skips over output changes unless `"pad-wo-active"` says a pad listens
  ("the counter only stops coasting over output changes while a pad selects one"). The CCL must
  assert that line (OR-ed with the pads) while an enabled LUT selects INSEL = TCC.
- **TC WO: missing.** `mchp-tc` has no waveform outputs ("Not modelled: ... waveform outputs on
  pins") and skips ticks freely. It needs a `"pad-wo"[2]` and `"pad-wo-active"[2]` like the TCC
  (the same lines would also give TC pads).
- **SERCOM TX bit stream: missing.** `mchp-sercom` works on bytes over a chardev. The CCL needs
  the PAD0 TX level over time (start, data, parity and stop bits at the baud rate, idle high), so
  the SERCOM would have to synthesize it on QEMU_CLOCK_VIRTUAL. Until then, INSEL = SERCOM can
  read idle (1 while enabled, 0 while disabled **[guess]**) and log LOG_UNIMP.
- **AC: missing** (see `ac-u2245.md`). A future `mchp-ac-u2245` should export `"cmp"[2]` levels.
- **Clock and timing**: a Clock input for GCLK_CCL. Without filter, edge detector, sequencer or
  event inputs, evaluate instantly on every input change. Otherwise schedule on QEMU_CLOCK_VIRTUAL
  at GCLK_CCL edges: delay lines of L cycles for SYNCH/FILTER (L from E13), 1-cycle pulses for
  the edge detector and the event strobe, flip-flop updates on the edge. Use event-driven timers,
  never per-cycle ticking: JK toggling at GCLK/2 on a 48 MHz clock means 24 M edges/s, so coalesce
  only while no observer (pad, event user, LINK) listens. LINK/FEEDBACK loops without any
  clocked stage are combinational oscillators on silicon. The model must detect and break them
  (log LOG_GUEST_ERROR, hold the output) rather than recurse.
- **Registers**: `overlays/ccl_u2225.yaml` with the protection in §2, `pac_protected` on every
  register, SWRST self-clearing, and a post_write hook on CTRL/LUTCTRL/SEQCTRL to re-evaluate.

## 6. Silicon test plan (bare EV15N46A, no external wiring)

Proposed firmware: `firmware/hello/tests/cclprobe.c` first (raw observations, prints values,
checks nothing, like `evprobe.c`), then `tests/ccl.c` (checks what the probe settled, ends with
`PP:EXIT <fails>`, runs unchanged on the twin). CPU at 48 MHz from OSC48M (`CPU_CLOCK_HZ`); SysTick
for timestamps (20.8 ns per tick). Enable the APB clocks of CCL (APBCMASK bit 23), EVSYS, the TCs,
TCCs, AC/DAC and SERCOM1/2 as each experiment needs, and GCLK PCHCTRL[32] for GCLK_CCL.

### 6.2 Read-back methods (all without a scope)

- **R1 OUT pad via PORT IN**: OUT pad muxed to CCL (PMUXEN, PMUX I) with INEN = 1. Read
  `PORT.IN`; `CTRL.SAMPLING` = 0 adds two PORT cycles of read latency.
- **R2 event counter**: LUTEO = 1. EVSYS channel k: EVGEN = 77+n, PATH = RESYNC (or SYNC),
  EDGSEL = RISING, GCLK_EVSYS_CHANNEL_k = GEN0 (48 MHz). User TCm_EVU = k+1, TCm COUNT16 with
  EVACT = COUNT (as `evprobe.c` does with TC1). Read COUNT after READSYNC. Pick m so TCm is not
  the CCL source under test. Keep edge rates well under GCLK_EVSYS/2, and read CHSTATUS/OVR to
  catch lost events.
- **R3 pin-less level copy**: EVSYS channel ASYNC from LUTOUT_n → USER PORT_EV_0 → PORT EVCTRL
  PID0 = 24, EVACT0 = OUT, PORTEI0. PORT.OUT bit 24 then follows the LUT output: a held level
  drives OUT (MC00 silicon, see `mchp_port.c`). LED0 (active low) shows it too, which is a free
  sanity check for a human watching. This is the only practical way to observe LUT3.
- **R4 slow-clock logic analyser**: put GCLK_CCL on a slow generator (OSCULP32K / 32 = 1024 Hz,
  about 977 µs per cycle). Poll R1 or R3 in a tight loop with SysTick timestamps and print
  transition times in GCLK cycles. This resolves filter latency, edge-pulse width and strobe
  width directly.
- **R5 EVSYS flags**: a sync/resync channel on LUTOUT_n with no user sets INTFLAG.EVD/OVR on
  edges. This is a cheap edge detector, as characterized in `evprobe.c`.

### 6.3 Input drivers

- **D1 MASK/TRUTH**: everything masked, so OUT = TRUTH[0]. Change TRUTH with the CCL disabled.
- **D2 pulls on a muxed IN pad**: PINCFG = PMUXEN | INEN | PULLEN, DIR = 0, PMUX I/J, then
  OUT = 1/0 selects pull-up/down. This is the only way to move an IO input on a bare board,
  because PMUXEN takes the pad from the PORT (§27.6.1). Allow about 20 µs to settle (internal pull
  with header capacitance). Confirm the level with PORT.IN on the same pad.
- **D3 TCC static and pulse levels**: TCCn NPWM, prescaler 1. CCx = 0 gives WO constant 0 (0 %
  duty; `tcc_update_wo()` uses `c > 0` when counting up); CCx > PER gives constant 1; CCx = k gives a
  k-cycle pulse each period (for E13 with GCLK_TCC on the CCL's generator). Silicon-only extras:
  PATT.PGEx/PGVx force WO, DRVCTRL.INVENx inverts, DRVCTRL.NREx/NRVx set the disabled state.
- **D4 TC WO[0]**: TCn MFRQ (toggle at a known rate) or NPWM CC0 = 0 / CC0 > TOP (COUNT8 PER) for
  static levels.
- **D5 events**: an async channel from TCm_OVF (known rate) or from AC_COMP_0 (a level) into
  CCL_LUTIN_n, plus CHANNEL.SWEVT (probe only).
- **D6 AC**: COMP0/1 MUXPOS = VSCALE, MUXNEG = DAC (errata: not INTREF). Move SCALERx, which is
  writable while enabled, or the DAC code across the trip point. Cross-check with STATUSA.STATEx.
  Setup as in `ac-u2245.md` §5.
- **D7 SERCOM TX**: SERCOM1/2 USART with TXPO = 0, TX on PAD0, **not muxed to any pin**. Send 0x55,
  0xAA and 0x00: 8N1 with LSB first gives 5, 4 and 1 rising edges per frame (0x00 rises only at
  the stop bit). Also SPI master with DOPO = 0 (MOSI on PAD0).
- **D8 internal**: LINK, FEEDBACK and JK/DFF toggling as clock sources (E10-E13).

## 7. Open questions only silicon can answer

1. Enable protection: is LUTCTRLn keyed to CTRL.ENABLE only, or also to LUTCTRLn.ENABLE ("can be
   written at the same time as LUTCTRLn.ENABLE is written to '1'")? Does a write while
   CTRL.ENABLE = 1 that sets LUTCTRLn.ENABLE together with other fields take effect? (E0)
2. Does SWRST read back 1 for a time? Which registers survive it? (E0)
3. What does an OUT pad do while its LUT or the CCL is disabled: driven 0 or released? (E1)
4. Does PULLEN act on a pad muxed to CCL IN? Does an IO input see a pad with PMUXEN = 0? Are two
   pads muxed to the same IN[x] OR-ed? (E2, E4)
5. TCC input tap point (after PATT, INVEN, dead time; state while the TCC is disabled). Is LUT3
   → TCC0 on MC00? (E5)
6. TC WO[0] tap point (INVEN0, COUNT32 slave). Do INSEL 0xA/0xB do anything on MC00 (IP 1.0.1)?
   (E6)
7. SERCOM "pad[0]": an internal signal or the pin? Does every INSELx = SERCOM see the same TX?
   (E7)
8. Is the AC input raw, filtered (FLEN) or synchronized? (E8)
9. EVENT strobe: width, behaviour with LUTEI = 0 and with GCLK_CCL off, response to SWEVT, and to
   the forbidden sync/resync paths. (E9)
10. LINK: does LUT3 wrap to LUT0? Does it tap before or after the filter/edge stage and the
    sequencer? (E10)
11. FEEDBACK with SEQSEL = DISABLE. (E11)
12. Sequencer: OUT0 = SEQ and OUT1 = raw LUT1? Are the latches asynchronous? What does S = R = 1
    do? Is the "write CTRL.ENABLE twice" rule (MC00-only text) needed? Which modes need GCLK_CCL?
    (E12)
13. Exact SYNCH and FILTER latency and FILTER's glitch-rejection width, against the DS's "two to
    five GCLK cycles". (E13)
14. Edge-detector pulse width. What happens with EDGESEL and no filter? (E14)
15. Standby forcing of clocked LUTs, and RUNSTDBY's enable protection. (E16, E0)

## 8. Answers from silicon (2026-10-21)

The desk EV15N46A ran `firmware/hello/tests/cclprobe.c` (C0-C9) and `cclprobe2.c` (D1-D7); the
model (`hw/misc/mchp_ccl.c`) follows these answers and `firmware/hello/tests/ccl.c` checks them on
both (`golden/pic32cm1216mc00048-a1/ccl-silicon.txt`). Open questions of section 7:

1. **Protection** (C0, C8, C9): SEQCTRL and CTRL.RUNSTDBY take writes only while CTRL.ENABLE is 0.
   LUTCTRLn's bits other than ENABLE take a write only while CTRL.ENABLE is 0 **and** the LUT was
   disabled before the write: a write that enables a LUT configures it, one that disables it
   changes only ENABLE, and with the CCL on even an enabling write takes only ENABLE. So "written
   at the same time as LUTCTRLn.ENABLE is written to 1" holds only with the CCL off. After
   CTRL.ENABLE = 0 a LUT that stays enabled never becomes writable (100000 tries).
2. **SWRST** reads 0 right after the write; the write masks match the ATDF (CTRL 0x43, SEQCTRL
   0x0F, LUTCTRL 0xFF7FFFB2).
3. **A disabled LUT, and a disabled CCL, drive the OUT pad to 0** (a pull-up does not show, C1).
4. **IO inputs need the pad muxed** to the CCL (a GPIO-driven pad reads 0, C3); the pull resistor
   works on a muxed input pad (C2). Two pads on one IN[x]: not tried.
5. **TCC input** (D1): IN x = WO[x] of TCC(n % 3), LUT3 = TCC0; TCC1 and TCC2 (two channels)
   give CC0's output on WO[2] as well. No pad mux needed. The pre/post-PATT/INVEN tap: not tried.
6. **TC input** (D2): TC = WO[0] of TCn, ALTTC = TC(n + 1); no pad mux needed.
7. **SERCOM input** reads 1 with SERCOM1 disabled and with it enabled and idle (D7).
8. **EVENT** (D6): every software event on an asynchronous channel gives one strobe on the
   output (10 of 10 counted); at a 1024 Hz GCLK_CCL the strobe came 2.5 cycles after the event
   and lasted less than the polling loop (well under a cycle).
9. **LINK** (C4): LUTn reads LUT n + 1; LUT3 wraps to LUT0. Before or after the sequencer: not
   settled.
10. **FEEDBACK** with SEQSEL = DISABLE reads 0 (C5).
11. **Sequencers** (C6): DFF and LATCH gate D with G; JK holds, clears, sets as tabled and with
    J = K = 1 toggles at GCLK/2 (1000 rising edges in 2 ms at 1 MHz, D5); RS sets, clears, holds,
    and S = R = 1 left it set. Disabling the even LUT clears the output; OUT1 stays the odd LUT's
    own output. CTRL.ENABLE written once worked as well as twice.
12. **Latency** at 1024 Hz (D3): none 1 us (combinational); SYNCH 1.3-2.0 cycles (the second
    GCLK edge); FILTER 3.2-4.1 cycles (the fourth). Glitch-rejection width: not measured.
13. **EDGESEL** with SYNCH (D4): one pulse of one GCLK cycle (997 us) per rising edge, none on a
    falling edge.
14. Standby: not probed.

## 9. The twin

`hw/misc/mchp_ccl.c` models section 8. The SoC taps TC/TCC waveform outputs and AC comparator
outputs for it (split from their pad lines, with "tap-*-active" OR-ed into the TC/TCC's
"pad-wo-active" so they stop coasting), wires IN pads through PORT "func-in" (the generic pad
input path: `pic32cm_connect_pad_inputs()`), and sets "tcc-count"/"ac-count" for the per-device
INSEL wiring. Clocked stages run on QEMU_CLOCK_VIRTUAL at GCLK_CCL edges, only while something is
pending. Twin differences: at 1024 Hz the filter latencies come about 0.2 cycle earlier than on
silicon (both inside the edge windows); the EVENT strobe is zero-width (a polling loop never sees
it; event counting does). Not modelled: the SERCOM TX bit stream, the JH01's ALT2TC and
ASYNCEVENT, standby, SYNCH passing a pulse shorter than two edges.
