# DAC (IP U2214): research notes for the twin

Gathered 2026-10-21 for the PIC32CM1216MC00048 (PIC32CM MC00 Curiosity Pro, EV15N46A); the
PIC32CM5164JH01100 carries the same IP (U2214 2.1.0 against the MC00's 2.0.1, a reviewed diff in
`docs/research/microchip-data.md`). The first round (`firmware/hello/tests/dac.c`, 2026-10-15)
covered DATA conversions, the references and READY; this one covers the data buffer.

Sources, most authoritative first: silicon (section 3), the data sheet **DS60001638E** chapter 39
(PDF pages 828-844, `C:\pp\datasheets\DS60001638E-PIC32CM-MC00.pdf`), the ATDF
(`PIC32CM-MC_DFP/1.4.67`, DAC instance and the event/DMA tables).

## 2. What the data sheet says

- DATABUF and DATA form a two-stage FIFO: a START event (EVCTRL.STARTEI, rising edge or falling
  with INVEI) moves DATABUF into DATA and converts (39.6.8.2). With STARTEI, "only DATABUF must be
  written".
- EMPTY: set when DATABUF moves into DATA, cleared by a DATABUF write or by writing 1. "As DATABUF
  is initially empty, a DMA request is generated whenever the DAC is enabled" (39.6.3).
- UNDERRUN: a START finding DATABUF empty (39.6.4).
- EMPTY event output with EVCTRL.EMPTYEO (39.6.5).
- DITHER: DATA[13:4] the code, DATA[3:0] the dither (DATA[15:6] and [5:2] with LEFTADJ), 16
  sub-conversions per value, "EMPTYx event and DMA request are therefore generated every 16
  DATABUF to DATA transfers" (39.6.8.4).
- Writes to DATA, DATABUF, ENABLE and SWRST are write-synchronized; "if an operation that requires
  synchronization is executed while its busy bit is one, the operation is discarded and an error
  is generated" (39.6.7).
- Enable-protected: CTRLB and EVCTRL (39.6.2.1). The EVCTRL register description (39.7.3) lists
  only PAC write protection: silicon sides with 39.6.2.1.

## 3. Answers from silicon (2026-10-21)

`firmware/hello/tests/dacprobe.c` (D1-D11), `dacprobe2.c` (E1-E7) and `dacprobe3.c` (G1-G4) on
the desk board; `dacbuf.c` checks them on both (`golden/pic32cm1216mc00048-a1/dacbuf-silicon.txt`).

1. **EMPTY at every enable**, with or without STARTEI, and even with DATABUF already written
   before the enable (D1, E4). It stays set until cleared (2 ms later still set, E1). SWRST clears
   it; disabling leaves it as it is.
2. **A DATA write clears EMPTY** too (D3, E1), and converts at once when DATABUF is empty.
3. **SYNCBUSY.DATA and DATABUF stay set from a DATABUF write until a START moves it** (G1: 0x0C
   until the START; a firmware wait on SYNCBUSY after a DATABUF write with STARTEI 0 never ends).
   Writes meanwhile are dropped: a second DATABUF write (D5, E3), a DATA write (G1). A DATABUF
   write while disabled is kept and moved by the first START after the enable (G1, E4).
4. **START with DATABUF full** moves it and sets EMPTY within about 0.7 us (E5). **START with
   DATABUF empty** sets UNDERRUN and EMPTY again, the output kept (D4). With STARTEI 0 a DATABUF
   write changes nothing at the output and START does nothing (D2).
5. **INVEI** with a software event (a pulse) still starts (D6).
6. **EVCTRL and CTRLB ignore writes while enabled** (D7).
7. **The EMPTY event** fires at the enable and at every START, underruns included; not at a
   DATABUF write (D8).
8. **DMA on EMPTY** (trigger 39, D9): the enable's EMPTY moves the first beat into DATABUF at once;
   each START then moves one value out and the next one in; after the last beat EMPTY stays set
   and the next START underruns.
9. **Dithering** (G2-G4): a full DATABUF moves at any START (B written after the first START was
   out at the second), but EMPTY comes on every 16th START counted from the enable (16, 32, ...),
   whatever moved when, and UNDERRUN only on the START opening a group (17, 33, ...) with DATABUF
   empty. The output's average follows the 14-bit value (300.5 and 600.25 read as expected); its
   sub-conversion steps are visible as one-code changes over the group.

Test firmware lesson: after `scope_start()` the SysTick period is 2^24 cycles, so `delay_ms()`
(which counts SysTick wraps) waits about 350 ms per millisecond; use `delay_us()` or
`scope_wait_until()` there. And a bounded wait that times out looks like a long delay: print
whether it timed out, not only how long it took.

## 4. The twin

`hw/misc/mchp_dac_u2214.c` models section 3: DATABUF with its busy state and dropped writes, START
on the INVEI edge, EMPTY and UNDERRUN as above (dithering's 16-START rhythm included), the EMPTY
event and the EMPTY DMA request (a level trigger on INTFLAG, wired by the SoC; setting EMPTY kicks
the DMAC). The dithered output is the 14-bit value's average. Not modelled: the sub-conversion
steps, the conversion time, VPD, standby (EMPTY set on wake-up), the error of a write dropped
during synchronization, silicon's offset of about 15 mV at code 0.
